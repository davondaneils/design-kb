# Color in UI systems: tokens, roles, themes, states

Turning a palette into a token system that survives light mode, dark mode, states and rebrands. Sources: `kb/research/color/04-ui-systems-themes.md`. Token names and roles follow `kb/FOUNDATIONS.md`.

## Fundamentals (non-negotiable)
1. **Two layers minimum.** Primitives (`--color-blue-600`) hold values. Semantic roles (`--color-primary`) reference primitives. Components use only semantic roles (FOUNDATIONS).
2. **The shared role set:** `bg`, `surface`, `surface-raised`, `text`, `text-muted`, `border`, `primary`, `on-primary`, `accent`, `success`, `warning`, `danger`, `info`, `focus-ring`, as `--color-{role}`. Variants use `--color-{role}-{variant}`: `-hover`, `-pressed`, `-subtle`, `-strong`.
3. **Every fill role has a paired content color that passes contrast** (Material's on-primary pattern). If you add `--color-danger` as a fill, you add its text pairing too.
4. **One color, one meaning** (Apple HIG). If brand blue is the link color, it is not also decoration on non-interactive text.
5. **Light and dark map the same roles to different primitives.** Dark mode is a remap, not an inversion (Apple HIG: dark colors "aren't necessarily inversions").
6. **Each state is checked:** default, hover, pressed, focus, selected, disabled, error, in both themes.

## Default mapping
Primitives come from the ladder in 02 (neutral at hue 260, chroma 0.015, with the 975 and 990 dark surface steps; primary blue at hue 260, chroma 0.20). Numbers are measured.

Why the dark theme keeps `primary` at 600 with white text: it passes both WCAG (5.46:1) and APCA (Lc 82). The Material-style alternative, a light primary (400) with dark text, scores 6.5:1 but only Lc 52. (Our measurement; either is legal.)

Why `primary-hover` goes darker in dark mode too: lightening a 600 fill toward 500 drops the white label to 3.5:1 (fails). Opinion: users do not notice the direction of a hover shift, only that it changes.

## CSS skeleton
```css
:root {
  color-scheme: light dark;
  /* primitives (generated by assets/oklch_scale.py, hex fallback in comments) */
  --color-neutral-50: oklch(97.5% 0.002 260);  /* #f6f7f8 */
  --color-neutral-600: oklch(53% 0.015 260);   /* #676c75 */
  --color-neutral-900: oklch(32% 0.010 260);   /* #303338 */
  --color-neutral-990: oklch(18% 0.006 260);   /* #101214 */
  --color-blue-300: oklch(81% 0.095 260);      /* #9dc2ff */
  --color-blue-600: oklch(53% 0.200 260);      /* #1463dc */
  --color-blue-700: oklch(46% 0.184 260);      /* #044fbc */
  /* semantic roles */
  --color-bg: light-dark(var(--color-neutral-50), var(--color-neutral-990));
  --color-text: light-dark(var(--color-neutral-900), var(--color-neutral-50));
  --color-text-muted: light-dark(var(--color-neutral-600), var(--color-neutral-300));
  --color-primary: var(--color-blue-600);
  --color-primary-hover: var(--color-blue-700);
  --color-on-primary: #fff;
  --color-accent: light-dark(var(--color-blue-600), var(--color-blue-300));
  --color-focus-ring: light-dark(var(--color-blue-600), var(--color-blue-300));
}
/* user override: <html data-theme="dark"> */
:root[data-theme="dark"] { color-scheme: dark; }
:root[data-theme="light"] { color-scheme: light; }
```
`light-dark()` is Baseline 2024. For older browsers, set the light values first and override inside `@media (prefers-color-scheme: dark)`. Ship hex fallbacks before OKLCH values if you support browsers older than May 2023.

## States
| State | Default (stepped) | Material alternative (overlay) |
|---|---|---|
| Hover | fill one step darker (600 to 700); subtle surfaces neutral-100 | content color overlay at 8% |
| Focus | 2px `--color-focus-ring`, 2px offset; never remove the outline without replacing it | overlay 12% plus ring |
| Pressed | two steps darker (800) | overlay 12% |
| Dragged | raise one elevation level | overlay 16% |
| Selected | `primary-subtle` (100) background, 800 text, plus a non-color mark (check, bar, weight) | |
| Disabled | neutral-100 fill, neutral-400 text, no hover; exempt from contrast | container 12% opacity, content 38% opacity |
| Error | danger-600 border and text, icon, message | |

Overlay values: material-web tokens. Stepped values: our default because they keep the contrast guarantees of the ladder (overlays on unknown backgrounds do not).

## Decision rules
- If you are building for a client who may rebrand: generate primitives from one hue and chroma; semantic roles never mention a hue name in components. A rebrand becomes a primitives swap (Linear runs whole themes from three inputs).
- If you use alpha colors (white text at 60%, translucent borders): the result changes with every surface underneath. Check the composited color on each surface it can sit on, both themes, or keep text on solid tokens. Translucent overlays (scrims, state layers) are fine when you check the result.
- If the colors go into email or older embeds: ship hex only (opinion; many email clients lack modern CSS color support, check caniemail.com).
- If a value has no role: add a variant to an existing role before inventing a role. New roles need a reason that survives both themes.
- If you need elevation in dark mode: lighter surface (990, 975, 950), not darker shadow (FOUNDATIONS; Apple base vs elevated; Material tonal surfaces).
- If the audience reads long text (docs, news, books): offer dark mode, do not default to it for general audiences; follow the OS setting (NN/g 2020: light mode reads better for most people with normal vision; dark can help some low vision users).
- If you offer a theme toggle: three options, Light, Dark, System, with System as default.
- If images or illustrations sit on dark surfaces: tone down large white areas, which glow (Apple HIG).
- If users enable more contrast: under `@media (prefers-contrast: more)` map `text-muted` to `text` values and `border` to `border-strong`.
- Charts and data viz: use the dataviz skill; keep chart colors separate from semantic roles so "red" in a chart never reads as "error".

## Expert moves
- **Lightness, not hue, carries the theme.** Keep hue and chroma per role across themes and change only the step. Brand recognition survives the switch.
- **Dark mode needs finer steps near black.** The 975 and 990 steps exist because 950 to 900 is too big a jump for three surface levels.
- **Desaturate large dark mode areas.** Surfaces at chroma 0.006 to 0.008 tinted to the brand hue look rich; colored dark surfaces above about 0.03 chroma look like a theme from 2012 (our opinion).
- **Test both themes at once.** Put light and dark side by side in the design file; every component review covers both.
- **`forced-colors`:** keep real (even transparent) borders on controls so shapes survive Windows contrast themes, and never encode state only in `background-color`.

## Do and don't
- Do: `.btn { background: var(--color-primary); color: var(--color-on-primary); }`. Don't: `.btn { background: var(--color-blue-600); }` or `#1463dc` in a component.
- Do: one semantic token per job (`--color-text-muted`). Don't: `--color-gray-text-light-2`.
- Do: dark surfaces 990 to 950. Don't: pure `#000` backgrounds with pure `#fff` text (21:1 causes halation for many readers; our opinion, in line with Apple and Material using dark gray).

## Worked example: "Set up light and dark tokens for a SaaS dashboard"
1. Generate primitives: neutral hue 260, chroma 0.015, `--neutral`; primary hue 260, chroma 0.20; red 25, green 150, amber 75 with `--shift -20`.
2. Map roles with the default mapping table. Sidebar uses `surface`, main canvas `bg`, cards `surface-raised`.
3. Status pills: `success-subtle` background (green-100), green-800 text, a dot icon; same pattern for warning and danger. Dark: 950 background of the hue, 200 text.
4. Tables: row hover neutral-100 (light) or neutral-975 to 950 (dark); selected row `primary-subtle` plus a 2px left bar in `primary`.
5. Charts: hand off to the dataviz skill; categorical palette distinct from status colors.
6. Verify: run `oklch_scale.py check` on each text role against each surface it can sit on, both themes. Fix anything under 4.5:1 (text) or 3:1 (borders, icons, focus).
